# v24

3連単の買い目を作って ntfy に通知する。10分ごとに動き、ネット締切まで4〜30分のレースだけ扱う。

引き継ぎメモ（`boatrace_hikitsugi.md`）の §0 で採用したルールをそのまま実装したもの。

---

## v23 と何が違うか

### 1. オッズがモデルの入力になった

これが最大の変更。v23 は朝に予想して ntfy の予約送信を登録できたが、v24 はできない。
展示が出て（締切30〜40分前）、オッズが動いてから予想する。

```
締切30分前  展示タイム・水面気象が出そろう
      ↓     波・風で足切り。落ちればオッズを取らない
      ↓     オッズ取得 → 予想 → 買い目
締切 4分前  ここまでに通知が飛んでいないと投票が間に合わない
```

### 2. モデルが3本から1本になった

v23 は p1/p2/p3 のカスケード。v24 は **1着だけモデル化して、2着3着は市場の条件付き構造を借りる**。

```
P(a,b,c) = q(a,b,c) × p1(a)/q1(a)      ← features.trifecta()
```

メモ §7-1c で検証済み。3連単の対数損失で市場を −0.0037 下回るところまで、
この形でそのまま乗る。p2/p3 を作る必要がない。

### 3. 学習と本番で出走表の取得元をそろえた（v23 のバグ修正）

v23 は本番の出走表を uchisankaku から取っていたため、学習データ（info.kyotei.fun 由来）と
中身が違っていた。

| | v23 の本番 | 学習データ | v24 |
|---|---|---|---|
| `avg_st` | **コース別STを代入** | 平均ST | 平均ST |
| `b_2ren` | **常に None** | ボート2連率 | ボート2連率 |

v24 は **出走表 = info.kyotei.fun / 今節成績 = uchisankaku** に分けた。学習側と同じ分担。

### 4. モーター純度が取れなければ異常終了する

v23 は取れなくても予想が出てしまい、ログを見ないと気づけなかった（メモ §1）。v24 は落とす。

### 5. 勝負レース(S8)・払戻フィルタを廃止

帯 `q 0.12〜0.25` に置き換えた。メモ §5 で「払戻フィルタの正体はオッズ帯の選択」と判明したため。

## 導入手順

### 1. モデルを作る（Colab）

```bash
!pip -q install lightgbm
!rm -rf v22 v24
!git clone --depth 1 https://github.com/honda1986/v22.git
!git clone --depth 1 https://github.com/honda1986/v24.git
!python v24/pure.py --kfile v22/kfile --out /content/pure.npz
!python v24/train.py --raw v22/raw --tokuten v22/tokuten \
                     --pure /content/pure.npz --out v24/model --cut 20250316
```

最後に出る **「市場 → モデル」の対数損失が市場を下回っていること**を必ず確認する。
上回っていたら投入しない。

できた `model/lgb_mf.txt` と `model/features.json` を v24 に commit する。

### 2. 動作確認（Colab、学習セルの続きに貼る）

**必ず `v24` の中に入ってから実行する。**`model/` `motor/` `cache/` を相対パスで見ているので、
`/content` のまま走らせると「model/features.json がありません」で止まる。

```python
%cd /content/v24

# ① 計算の筋道だけ確認する（ネットに出ない。すぐ終わる）
!python selftest.py

# ② モーター純度を作る（本番は motor.yml が毎朝やる。ここでは手で作る）
!python motor.py --kfile ../v22/kfile --out motor/latest.json

# ③ 通知せず、買い目だけ出す
!python yosou.py --dry --win 4,45
```

`--win 4,45` は動作確認のときだけ使う。締切4〜45分前を対象にするという意味で、
本番の4〜30分より少し広くとって、レースが引っかかりやすくしてある。

**次の3つが順に出れば成功。**

1. `selftest.py` の最後が `すべて通りました`
   - `model/features.json がまだありません` → 学習（手順1）が終わっていない
   - `★モデルの特徴量が features.py と食い違っています` → モデルを作り直す
2. `motor.py` が `motor/latest.json` を書く
3. `yosou.py --dry` が場名の並んだログを出す

```
20260822 の予想を作ります (特徴量 57個)
モーター純度 20260821 1,251人
対象の場 15場 (淡水9場は除外)
締切4〜45分前のレース 9件
  大村 5R (あと22分) ★2点  波1cm 風2m  1-2-3(p/q 1.12) 1-2-4(p/q 1.08)
  常滑 8R (あと17分) 見送り  波4.0 風3.0
  唐津 3R (あと38分) 買い目なし  波1cm 風2m
通知 0件
```

**「見送り」「買い目なし」ばかりでも正常。**買うのは全レースの4.4%しかない。
`★` が1本も出ないまま終わるほうが普通で、それは失敗ではない。

**`締切4〜45分前のレース 0件` はレースをやっていない時間帯。**
昼（日本時間 11:00〜20:00）にもう一度実行する。Colab の時計はUTCだが
`yosou.py` は中で日本時間に直しているので、そこは気にしなくていい。

### 3. GitHub の設定

- Secrets に `NTFY_TOPIC` を入れる
- Actions の書き込み権限を有効にする（`state/` と `cache/` を commit するため）
- `.github/workflows/motor.yml` … 1日1回 6:00 JST。モーター純度を作る
- `.github/workflows/yosou.yml` … 10分ごと。1ジョブ内で3分おきに3回まわす

### 4. ★ 本番投入の前に必ず確かめること

選別ルールの波高・風速のしきい値は、**Kファイル（レース後の記録値）で検証した**もの。
実運用では直前情報の値を使う。**両者の分布が一致するか確かめること。**

```bash
python collect_before.py --date 20260821    # 直前情報を1日ぶん取る
# その日の kfile の波高・風速と突き合わせて、ずれていないか見る
```

ずれていたら `select_rule.py` の `WAVE_MAX` / `WIND_MAX` を合わせ直す。

  食い違うと yosou.py は起動時に落ちる
- **「モーター純度」が出ずに落ちたら** `motor.yml` が失敗している
- 「見送り」が続くのは正常。対象は全レースの4.4%（1日6.6レース）

## 承知しておくこと

- **淡水がなぜ悪いのかは分かっていない**（メモ §11）。芦屋は1号艇1着率が全場最高（59.6%）
  なのに回収率は最低（78.4%）で、「本命が来やすいから」では説明できない。
  機序が説明できない効果は将来消える可能性が相対的に高い
- GitHub Actions の schedule は遅延する。3回まわしているが、それでも落ちる回はある
- `state/notified_*.json` を commit しているので、push が失敗すると二重通知があり得る
