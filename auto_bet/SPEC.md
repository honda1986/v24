## 0. 前提

**テレボートの『電話投票に関する約定』は、利用者本人が確認済み（2026-09-18）。**
自動操作について問題ないという判断のもとで、この仕様書は書かれています。

ただし約定は改定されます。**長く運用するなら、ときどき読み直してください。**

## 1. 全体の形

```
GitHub Actions (v24)          ご自身の Windows PC
  yosou.py が3分おきに予想        auto_bet が2分おきに取りに行く
        ↓                                ↓
  history.json を push  ──────→  買うべきレースを選ぶ
  (main ブランチ)                        ↓
                                 Chrome を操作して投票
                                        ↓
                                 bet_done.json に即記録
```

**予想側（GitHub Actions / v24）はいっさい触らないこと。** `history.json` を読むだけ。
書き込むと、予想側の push と衝突して記録が壊れます。

## 2. 入力：history.json の読み方 ★ここが本書の核心

取得先（公開リポジトリなので認証不要）:

```
https://raw.githubusercontent.com/honda1986/v24/main/history.json?t=<毎回変わる数>
```

### ★キャッシュに必ず引っかかる（見落とすと動かない）

`raw.githubusercontent.com` は **最大5分ほどキャッシュされます。**
`Cache-Control: no-cache` ヘッダだけでは足りません（CDN 側に効かない）。

**URL の末尾に毎回変わるクエリを付けること。** 予想サイトの index.html も
`fetch("history.json?" + Date.now())` としていて、同じ理由です。

```
url + "?t=" + str(int(time.time()))
```

それでも数分は遅れうるので、締切ギリギリのレースは取り逃すことがあります。
これは仕組み上の限界で、実害は「たまに買えない」だけ。**買いすぎる方向には転びません。**

### push が遅れることもある

予想側の push は失敗することがあり、ログに「push できず(次周に持ち越し)」と出ます。
その場合、通知は届いているのに history.json にはまだ載っていません。
**通知が来たのに自動投票が動かない、は正常な場合があります。**

### 2-1. 構造

```
{
  "updated": "2026-09-18T11:20:03",
  "days": [
    {
      "date": "20260918",          ← JST の日付。文字列
      "picks": [ ... ],            ← 帯（本番の買い目）
      "ana":   [ ... ],            ← 穴側（試験運用）★既定では買わない
                                   ★2026-09-20 以降 "shadow": true が付く。
                                     付いている回は buy_ana に関わらず買わない
      "races": [ ... ],            ← 見ただけのレース。投票には使わない
      "skipped": {...}, "runs": 12, "last_run": "11:20"
    }, ...
  ]
}
```

`days` は日付昇順。**今日の `date` に一致する要素だけ**を見ること。
`ana` キーは存在しない日がある（`day.get("ana") or []` で扱う）。

### 2-2. picks / ana の1件

```
{
  "jcd": 24,                  ← 場コード。下の表で場名に変換する
  "place": "大村",            ← 場名（そのまま使ってよい）
  "rno": 9,                   ← レース番号 1〜12
  "close": "15:00",           ← ★ネット締切（本場締切の3分前）。JST の "HH:MM"
  "buys": [
    {"combo": "2-1-4",        ← ★これが買う組。3連単。"1着-2着-3着"
     "odds": 12.9,            ← 通知した時点のオッズ。参考値
     "q": 0.058, "p": 0.072, "pq": 1.24}
  ],
  "cost": 100,                ← 1点100円 × 点数
  "combo": null, "pay": null, "hit": null, "ret": null   ← 翌朝 settle が埋める
}
```

**投票に必要なのは `jcd`（または `place`）/ `rno` / `close` / `buys[].combo` だけ。**
他は無視してよい。

`ana` の1件も同じ形で、加えて `"omin"`（そのレースの最低オッズ）が入る。

### ★投票の時点でオッズを見直さないこと

`buys[].odds` は**通知した時点**のオッズです。投票する頃には動いています。
だからといって **「いまのオッズで p/q を計算し直して、条件を満たさなければ買わない」
という実装にしないでください。**

理由: v24 は通知した時点の判断で買う前提で検証されています。
投票時に再判定すると**検証していない別のルール**になり、成績が何を意味するのか
分からなくなります。オッズが動いたぶんの目減りは、予想側が別途計測しています（§19）。

**通知された組を、そのまま買う。** それだけ。

### 2-3. close の意味（間違えやすい）

- `close` は **ネット投票の締切**。公式の本場締切より **3分早い** 値が既に入っている
- したがって `close` を過ぎたら**もう買えない**。`close` を最終期限として扱うこと
- 値は JST。PC の時計も JST 前提
- ミッドナイト開催があるため、遅い時間（23時台）のレースも出る
- **日付をまたぐレースは、実際には出てきません。** v24 自身の締切計算が
  日跨ぎに対応しておらず、そういうレースは通知されないため。
  ただし**それに依存した書き方をしないこと**。
  締切までの分数が大きく負（例 −60分より小さい）なら、
  「もう過ぎた」として黙って飛ばす実装にしておく
- **PC の時計とタイムゾーンが JST であること。** ずれると全部狂います。
  Windows の「時刻を自動的に設定する」がオンか確認してください

### 2-3b. 取得についての細かいこと

- `days` は**古い日も消えません**。日が経つほどファイルが育ちます。
  毎回まるごと取るので、通信量が気になるようなら
  「今日の `date` の要素だけ取り出して、あとは捨てる」実装にしておくとよい
- リポジトリが非公開に変わったら raw では取れません。
  そのときは読み取り専用のトークンが要ります（いまは公開なので不要）

### 2-4. 場コード

```
1桐生 2戸田 3江戸川 4平和島 5多摩川 6浜名湖 7蒲郡 8常滑 9津 10三国
11びわこ 12住之江 13尼崎 14鳴門 15丸亀 16児島 17宮島 18徳山 19下関
20若松 21芦屋 22福岡 23唐津 24大村
```

ただし **1,2,5,10,11,12,13,21,23（淡水9場）は v24 が最初から除外**しているので、
history.json に出てきません。実装側で気にする必要はない。

### 2-5. 1レースの点数

検証期間での実測（1レースあたり）:

★2026-09-21 に取り直しました（帯 p/q>1.14・波風の足切りなし、穴側 p/q>1.15）。

| | 1点 | 2点 | 3点 | 平均 | 最大 |
|---|---|---|---|---|---|
| 帯 | 2,755 | 183 | 1 | 1.06点 | **3点** |
| 穴側 | 449 | 55 | 4 | 1.12点 | **3点** |

**帯も穴側も3点が実測の上限**（帯の3点は 2,939レース中1レースだけ）。
4点以上が来たら異常なので、そのレースごと見送って警告を出すこと（→ 4-3）。
設定の既定値 `max_points_per_race: 4` はその想定。

## 3. 動作モード

4つ用意すること。**既定を `live` にしないこと。**

| モード | 何をするか |
|---|---|
| `login` | Chrome を開いて止まる。**手でログインしてもらう**。プロファイルに残す |
| `check` | ブラウザを開かず、いま買うべきレースを一覧表示するだけ |
| `dry` | ブラウザを開き、投票画面の一歩手前まで進んで**押さない** |
| `live` | 実際に投票する |

`live` は **設定ファイルの確認フラグが true のときだけ**起動を許すこと。
false なら理由を表示して終了。理由の文面に「約定を自分で読むこと」を必ず入れる。

## 4. 安全要件 ★実装で手を抜かないところ

### 4-1. 認証情報を保存しない

加入者番号・暗証番号を**ファイルにも環境変数にもコードにも置かない。**

Playwright の `launch_persistent_context(user_data_dir=...)` で
**専用の Chrome プロファイル**を1つ作り、`login` モードで手動ログインしてもらう。
以降はそのプロファイルを起動するだけ。セッションが切れたら `login` をやり直す。

- ヘッドレスにしない（`headless=False`）。画面が見えるほうが事故に気づける
- プロファイルのフォルダは `.gitignore` に入れる。**絶対に共有しない**

### 4-2. 二重投票を最優先で防ぐ

これがいちばん怖い事故です。

- 投票キーは `日付-場コード-R-組-種別`（例 `20260918-24-9-2-1-4-帯`）
- **同じレースが `picks` と `ana` の両方に出ることがあります**（225日で92レース）。
  これは正常。帯と穴側は別勘定なので、**レース単位で重複排除しないこと。**
  キーに種別が入っているのはこのため
- **投票が成功したら、その場で即ファイルに書く。** まとめて最後に書かない
  （途中で落ちると「投票済みなのに記録に無い」＝次の周で二重投票になる）
- 書き込みは一時ファイル → `os.replace` で原子的に
- 起動時に必ず読み込む。ファイルが壊れていたら**空で続行せず、止まる**

### 4-3. 締切と点数のガード

- 締切まで **N分未満なら投票しない**（既定3分。押している途中で締め切られるのを防ぐ）
- 締切まで **M分を超えていたら投票しない**（既定25分。オッズがまだ動く）
  - ★v24 側は 2026-09-21 から**締切15分前**に判定するので、届く買い目は15分前以降。
    25分のままで整合している（狭める必要はない）
- 1レースの点数が想定を超えていたら、そのレースごと見送って**警告を出す**

### 4-4. 上限（★あとから変えられるようにする）

**設定ファイルに置き、「無制限」も選べるようにすること。**

```
max_yen_per_day     1日の上限（円）。null なら無制限
max_points_per_race 1レースの上限点数。null なら無制限
bet_yen             1点あたり（100固定でよい）
```

上限は使いすぎ防止ではなく **バグ避け**です。
ループが暴走したり二重投票の判定が壊れたときに、残高を一度に溶かさないための保険。
入金額そのものが本来の上限なので、最初は残高より少し下に置いて、
慣れたら `null` にする、という使い方を想定しています。

1日の使用額は `bet_done.json` から当日分を合計して数えること。

### 4-5. 止める手段

- フォルダに `STOP` という名前のファイルが現れたら、次の周で終了する
- Ctrl+C で止めたときも、記録を壊さず終わる

### 4-6. 例外は「止める」

画面操作の途中で例外が出たら、**その周で処理を打ち切る**こと。
次のレースへ進まない。画面が中途半端な状態のまま次を操作すると、
違うレースに投票する事故が起きます。ログに「手で確認してください」と出す。

### 4-7. ログ

1行1イベントでファイルに追記。最低限これを残す。

```
時刻 / モード / 場・R / 種別 / 組 / 点数 / 金額 / 結果（投票した・見送った・失敗）
```

## 5. テレボートの画面操作（セレクタの取り方）

**私はテレボートの画面を見られないので、セレクタは書けません。** ご自身で採取してください。

```
pip install playwright
playwright install chromium
playwright codegen --channel=chrome https://www.telebo.../
```

`codegen` は**あなたの操作をそのままコードにして表示します**。

1. `codegen` を起動する
2. 手でログインする
3. 適当なレースで **100円ぶんの舟券を実際に1つ買ってみる**（3連単1点）
4. 表示されたコードをコピーする

これで「場を選ぶ→レースを選ぶ→3連単を選ぶ→組を入れる→金額を入れる→投票→確認」の
各ステップのセレクタが全部揃います。

**採取した操作は `telebote_page.py` のような1ファイルに閉じ込めること。**
サイトの作りが変わったとき、直すのがそこだけで済みます。
`auto_bet` 本体はそのファイルを `bet(レース情報, 金額, live) -> bool` の形で呼ぶだけにする。

### 画面操作で気をつけること

- **投票の確認画面で、組・金額・レースが自分の意図と一致しているかをコードで読み返して照合する。**
  一致しなければ押さずに中止。これが最後の砦です
- `dry` モードは「確認画面まで出して押さない」で実装する。
  確認画面のスクリーンショットを保存しておくと、あとで検算できます
- 待ち時間は固定秒ではなく、要素が出るのを待つ（`wait_for_selector`）

## 6. 段階的に上げていく順番

いきなり `live` にしないこと。

1. **`check` を1週間** — 「いま買うべき」の判定が history.json と合っているか、目で確認
2. **`dry` を1週間** — 画面が最後まで正しく進むか。確認画面のスクショを毎回見る
3. **`live` で1日1レースだけ** — `max_yen_per_day` を100円にして1点だけ通す
4. **上限を少しずつ上げる**

## 7. テスト（実装させるときに必ず言うこと）

サイトを触らずに確かめられるものは、全部そこで確かめる。

- history.json を手で作った偽データで、**選ばれるレースが正しいか**
  - 締切2分前 → 選ばれない／締切10分前 → 選ばれる／締切30分前 → 選ばれない
  - 既に `bet_done.json` にある組 → 選ばれない
  - 1日の上限に達している → 何も選ばれない
  - `ana` キーが無い日 → 落ちない
  - 今日の日付が `days` に無い → 落ちない
  - history.json が取れない（ネット断） → **その周は何もせず次へ**。落ちない
- `bet_done.json` が壊れている → 起動しない（空で続行しない）
- 画面操作は偽のページオブジェクトを差し込んで、本体のロジックだけ回す

## 9. 現時点の成績（実装の前に知っておくこと）

自動化する価値があるかは、まだ確定していません。

★2026-09-21 に入れ替えました。古い「帯 100.6% / 穴側 153.6%」は
**p/q>1.097・波風の足切りあり**の頃の数字で、いまのルールのものではありません。

| | 検証値 | 的中数 | 注意 |
|---|---|---|---|
| 帯（本番）p/q>1.14 | 102.4%（3,124点） | 635本 | 確定オッズでの値。実運用は下がる |
| 穴側（試験）p/q>1.15 | 124.9%（571点） | 62本 | 通し17か月の値。**独立10か月だけなら 87.5%** |

帯は、しきい値決定に使っていない10か月でも 102.5% と一致していて、
**期間をまたいで再現しています**（探索期間 102.3% / 独立期間 102.5%）。
それでも確定オッズでの値なので、実運用はここから下がります。

穴側は独立10か月で 87.5% しか出ず、事前登録の判定表では「**再現せず**」でした。

したがって:

- **まず帯だけで `dry` を回して、仕組みを確かめる**のが正しい順番
- **穴側は 2026-09-20 からシャドー**（記録のみ・通知も投票もしない）。
  `history.json` の `ana` に `"shadow": true` が付き、`selector.sources` が弾く。
  `buy_ana` を有効にしても買わない（`tests/test_parts.py` の `TestShadow` が担保）
- 穴側を `live` に戻してよいのは、**シャドーの記録が的中50本たまって、
  回収率125%以上かつ P(>100%)≥0.95 を満たしたとき**（`ana_howto.md` §8 の事前登録）。
  いまのペースで**15か月ほど**かかる。「半年」ではない
- 設定で**帯と穴側を別々にオン/オフできるようにしておくこと**（穴側は既定オフ）
